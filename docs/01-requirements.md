# Requirements Specification — Room Shopping List

เอกสารนี้เป็นขั้นตอน **Requirements** ของ SDLC สำหรับระบบจดลิสต์ซื้อของเข้าห้องรายเดือน

## 1. ภาพรวมระบบ (Overview)
ระบบช่วยผู้ใช้จดบันทึกรายการของที่ซื้อเข้าห้องในแต่ละเดือน เก็บจำนวน ราคา และวันหมดของแต่ละรายการ
พร้อมสรุปยอดเงินรายเดือนและแจ้งรายการที่ใกล้หมด

## 2. ผู้มีส่วนเกี่ยวข้อง (Stakeholders / Actors)
| Actor | คำอธิบาย |
|-------|----------|
| User (เจ้าของห้อง) | ผู้ใช้งานหลัก จดและดูรายการซื้อของ (ระยะแรกเป็น single-user ไม่มีระบบ login) |

## 3. Functional Requirements
| ID | ความต้องการ | Priority |
|----|-------------|----------|
| FR-01 | สร้าง/ดู/แก้ไข/ลบ "เดือนซื้อของ" (เช่น ตุลาคม 2026) | Must |
| FR-02 | สร้าง/ดู/แก้ไข/ลบ "รายการของ" ภายในเดือน | Must |
| FR-03 | แต่ละรายการเก็บ: ชื่อของ, จำนวนชิ้น, ราคาต่อหน่วย, วันหมด | Must |
| FR-04 | คำนวณยอดรวมเงินของแต่ละเดือน (sum ของ จำนวน × ราคาต่อหน่วย) | Must |
| FR-05 | แสดงรายการที่ "ใกล้หมด" (วันหมดอยู่ภายใน N วันข้างหน้า) | Must |
| FR-06 | ดูสรุปภาพรวมทุกเดือน (ยอดรวมแต่ละเดือน) | Should |

## 4. Non-Functional Requirements
| ID | ความต้องการ |
|----|-------------|
| NFR-01 | สถาปัตยกรรมแบบ Microservice แยกแต่ละ service ชัดเจน |
| NFR-02 | Database-per-service (แต่ละ service มีฐานข้อมูลของตัวเอง ไม่อ่านข้าม DB) |
| NFR-03 | สื่อสารระหว่าง service และกับ client ผ่าน REST ผ่าน API Gateway |
| NFR-04 | โค้ดออกแบบด้วยแนวคิด OOP (encapsulation, มี domain model, แยก layer ชัดเจน) |
| NFR-05 | รันได้ด้วย Docker Compose ในเครื่อง dev |
| NFR-06 | มี input validation และ error handling ที่เหมาะสม |

## 5. Use Cases (ย่อ)
- **UC-01 จัดการเดือน**: User เพิ่มเดือนใหม่ → ระบบบันทึก → แสดงในรายการเดือน
- **UC-02 จัดการรายการของ**: User เลือกเดือน → เพิ่ม/แก้/ลบรายการ → ระบบอัปเดต
- **UC-03 ดูยอดรวม**: User เลือกเดือน → ระบบคำนวณยอดรวม → แสดงผล
- **UC-04 ดูของใกล้หมด**: User เปิดหน้า dashboard → ระบบคืนรายการที่วันหมดใกล้ถึง

## 6. ขอบเขตที่ยังไม่รวมในเฟสนี้ (Out of Scope)
- ระบบ login / multi-user / authentication
- Push notification (ใช้การแสดงผลในแอปแทน)
- Message broker (ใช้ REST ไปก่อน ตามที่ตกลง)
